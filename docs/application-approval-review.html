Direct application approval and Lab placement

Implemented in the local preview and isolated staging database jxijdjmjuzslmjxolhjl. Production has not been deployed. The hosted application and draft GitHub PR have not been updated in this checkpoint.

Problem and root cause

The previous flow was application → shortlist → separate formation/offer → member acceptance → readiness → Lab access. Shortlist only wrote a review status. The dashboard's awaiting-review link filtered to new, so a shortlisted record left that immediate queue without initiating placement. It remained under Shortlisted/All, but the continuation was unclear.

Resulting flow

Decision / arrangementResult
Approve SoloUse the existing formation service to create one Solo placement and assign its role and owner. The approved membership enters preparation directly, with no offer or second administrative decision. Member confirmation of responsibilities/commitment, repository verification and existing readiness checks remain mandatory.
Approve TeamPlace directly in an explicitly selected forming team, subject to capacity, or enter the existing approved formation pool. Existing group formation accepts approved applicants without reapproval. Coordinator willingness/agreement, role coverage and minimum sizes are preserved.
Approve FlexibleRecord exactly one intended Solo or Team route using the existing placement choices. The submitted application remains Flexible. Existing historical placements retain their actual route and role even if a contradictory new choice is submitted.

Placement blockedRetain approval and a private administrator error. Retry placement using the saved decision. A savepoint rolls back partial Lab writes. A complete request cancellation rolls back the transaction and can be retried idempotently.

Reliability, permissions and participation

  • Existing sorted per-member transaction locks are acquired before application/team locks. The unchanged authoritative entitlement and membership triggers enforce three qualifying Labs across core and Market routes.
  • Paused Labs, accepted places and unexpired offers count. Completed, expired/declined and fully exited places do not. Departures retain a slot until required external access revocation is complete. An approved waiting-pool application has no membership or guaranteed place and reserves no slot; placement checks the allowance again.
  • Repeated approval returns the stored outcome. Existing memberships/offers are reused and never silently converted or deleted. A unique deterministic Solo reference, application lock and current-placement checks prevent duplicate creation.
  • The narrowly scoped membership hook applies only to explicitly approved official applicants being newly placed. It records the submitted application timestamp as the participation request; it does not forge a member response or mark commitment, access or admission complete. Existing legacy offers and Market consent remain unchanged.
  • Verified, allowed project administrators are required at the database boundary. Anonymous and ordinary-member approval attempts fail. The API also rejects foreign origins and unsigned requests.
  • Approval and outcome events use the existing private audit and notification infrastructure. One approval email event is queued; role/preparation updates and Lab-ready notices reuse current events. Private notes and database errors are excluded from member/email projections. No delivery scheduler, billing or automatic operational email sending was activated.

Database and API changes

Three tracked staging migrations add approved and six related fields to private_website_lab.interest_reviews: placement route, state, team, role, private error and approval timestamp. No historical rows are automatically approved or bulk rewritten.

New POST /api/admin/project-approval calls the verified-administrator RPC website_project_approval for approve/retry. Existing review and formation APIs remain available for legacy records. The public wrapper is security invoker; privileged helpers stay in the private schema with explicit grants and empty search paths.

Eight existing database functions receive targeted compatibility/projection changes; four functions are added. All other 87 audited function definitions, including Market, readiness, entitlement guards, core control and workspace services, retain their hashes. Market/portfolio source files match the pre-work UI checkpoint; the shared journey component has a regression test preserving Market's own consent stages.

Failures investigated

The old formation test assumed a manual start after readiness had already activated the Lab. The same error was reproduced with the original function definitions. Only those stale test expectations were corrected; readiness behaviour was not changed. An artificial 30-second race delay exceeded the existing API statement timeout and rolled back both test requests; it was replaced by a three-second bounded probe for the successful overlapping-request test.

Migration safety and rollback

Apply the three migrations in filename order through the normal release process. Do not rerun their SQL manually. Schema additions preserve legacy statuses and offers. If a release needs to be withdrawn after approvals exist, prefer a compatible forward fix or disable new decisions at the interface while retaining these records. Do not drop the new fields/status or restore a constraint excluding Approved while approved records exist. A destructive schema rollback requires an audited mapping of those decisions first; no such rollback was run.

Limits and handoff

  • Team waiting does not guarantee immediate placement, capacity or a reserved participation slot.
  • Email event capture and safe content were tested; no external operational email was sent. Existing delivery gates remain unchanged.
  • Database tests invoke real staging functions with isolated identities. Browser tests cover administrator actions; this is not a claim that every full member signup-to-completion journey was repeated through the browser.
  • Hosted frontend deployment remains separate. The draft GitHub PR was not updated because the available GitHub CLI session is signed out; no credentials were extracted or production changes made.
  • The staging security baseline still reports existing definer-function reviews and disabled leaked-password protection. No new warnings were introduced. Supabase advisor reference.
